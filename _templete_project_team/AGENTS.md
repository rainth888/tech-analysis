# AGENTS.md —— 多角色团队项目通用操作宪法（以 Git 版本控制为核心 · 开发工具无关版）

本文件是本团队项目仓库模板的通用最高操作指南与工程宪法，适用于任何 AI 辅助开发工具与大模型环境（包括但不限于 Cursor、Codex、Qoder、Antigravity、Windsurf、Cline、Claude Code、OpenCode、GitHub Copilot 及各类通用 Agent 平台）。本文件定义了**以 Git 为核心基本版本控制的项目开发机制**、通用目录结构规范、多角色职责边界、多环境并行工作机制、硬性工程约束、稳定主分支与稳定功能保护、深度问题分析与需求探问协议、命令执行安全规则以及任务状态跟踪体系，以确保一致性并防范高风险错误。

## 1. 以 Git 为核心基本版本控制的项目开发机制（Git-Centric Project Development Mechanism）

**本项目文件夹的核心运行底座是 Git 版本控制机制。** 所有需求基线、架构契约、业务源码、自动化测试、部署清单、角色交接单与任务状态变更，均以 Git 仓库的分支（Branch）、工作树（Worktree）、暂存区（Index）、提交历史（Commit）与标签（Tag）作为唯一权威的真相来源（Single Source of Truth）与协同边界。

### 1.1 仓库边界识别与 Git 前置检查（Mandatory Git Root Check）

- 在执行任何 Git 操作或文件修改前，**必须首先运行 `git rev-parse --show-toplevel` 并检查当前分支（`git branch --show-current`）**，以确认当前实际所属的项目 Git 仓库根目录及其稳定主分支。
- 当存在嵌套仓库（Nested Repositories）或子模块时，**绝不可**将父级目录仓库的 `master`、`main` 或其他分支误认为当前项目的稳定分支。
- 所有未纳入 Git 版本控制（或未按 `.gitignore` 明确排除）的散乱文件，均视为非法产物；严禁脱离 Git 提交历史通过口头或临时文件传递工程交付物。

### 1.2 稳定主分支保护制度（Stable Main Branch Protection — Mandatory）

- **`main` 分支仅作为稳定发布基线（Stable Release Baseline）**：严禁直接在 `main` 分支上修改任何应用程序代码、配置文件、脚本、工程文档或静态资源；严禁使用 `main` 分支进行新功能开发、缺陷修复、代码重构、性能调优、技术实验或迭代验证。
- **强制拉取专用工作分支**：在实现任何新功能、修复缺陷或执行改进前，必须从最新的基线分支创建并切换到专用分支（例如个人/单任务场景从最新 `main` 拉取 `feature/<name>` 或 `fix/<name>`；多角色团队迭代场景从 `develop` 或最新 `main` 拉取带任务与角色标识的 `feature/Txx-be`、`feature/Txx-fe`、`fix/IS-xxx`、`test/Txx-qa`、`ops/Txx-ops`、`docs/Txx-po`）。所有文件编辑、编译构建、联调调试、部署测试以及功能或硬件验收，**必须在专用分支上进行**。
- **合并入 `main` 的严格门禁**：仅当专用分支（或汇合后的集成分支）已完成全部规定的验证、涉及硬件或界面的行为已由用户完成物理/实机验收（如适用）、且**用户已明确确认该分支的精确版本稳定并批准合并**后，才允许合并入 `main`。
- **未通过验证禁止合并**：在验证失败、验证尚未完成或仍在等待用户物理/业务验收期间，**严禁**将分支合并入 `main`。
- **保持验证提交与文件树完全一致**：合并操作必须原封不动地保留经验证通过的精确提交（Exact Verified Commit）及结果文件树。严禁在合并过程中或合并之后夹带未经验证的清理、格式化或附带修改。如果在合并后发现新问题，必须重新创建新的修复分支（`fix/<name>`），经完整验证并获用户验收批准后，方可再次合并。
- **处于 `main` 分支时的强制动作**：如果当前处于 `main` 分支而用户提出了代码实现或文件修改请求，**必须在修改任何文件之前先创建并切换到专用分支**。在 `main` 分支上，仅允许执行只读检查、稳定版本的构建/部署/回归检查，以及合并已经过用户明确验收批准的分支。

### 1.3 团队多角色 Git 分支拓扑与版本溯源规范

| 分支类型                  | 命名规范示例                       | 拥有/操作角色        | 用途与合并流向规则                                                                           |
| :------------------------ | :--------------------------------- | :------------------- | :------------------------------------------------------------------------------------------- |
| **稳定发布主分支**        | `main`                             | `PM` + `OPS`（受控） | 仅存放送审通过并经真人批准的稳定基线版本，每次合入须打版本标签 `vX.Y.Z`                      |
| **团队日常集成分支**      | `develop`                          | 全体角色（经评审）   | 日常迭代各角色专用分支的汇合基线；合入 `develop` 后触发 `OPS` 部署至 `test` 环境供 `QA` 测试 |
| **角色/任务专用开发分支** | `feature/T21-be`、`feature/T21-fe` | 对应开发角色         | 单个任务卡（`Txx`）在单一角色下的独立开发分支，自检通过后合并入 `develop`                    |
| **缺陷修复分支**          | `fix/IS-20261110-002-be`           | 缺陷责任角色         | 针对 `QA` 提报的缺陷单（`IS-xxx`）创建的修复分支，须含失败复现单测与修复代码                 |
| **测试与运维分支**        | `test/T21-qa`、`ops/T21-deploy`    | `QA` / `OPS`         | 自动化测试脚本、CI/CD 流水线与部署编排专用分支                                               |

- **规范化提交信息（Commit Message）**：每次提交必须包含任务编号与角色标识，格式为 `[<ROLE>][<Task-ID/Issue-ID>] <type>: <简明中文说明>`（例如：`[BE][T21] feat: 实现工单退回补充与重新提交接口`）。
- **测试与部署版本铁律**：`QA` 严禁测试无明确 Git Commit SHA 溯源的构建产物；`OPS` 在每次发布 `/deployed` 或 `/ready` 报告时，必须明确记录对应的 Git 分支名与短提交号（Commit SHA）。

## 2. 通用项目目录结构规范（Universal Project Layout）

为保持目录整洁，必须严格遵守以下文件夹约定。**严禁**在根目录直接放置临时脚本、散乱的 Markdown 文件或未纳入 Git 追踪的资源。本模板采用**“根级控制区 + `z-*` 治理与规范区 + `docs/` 全生命周期工程文档区 + 分角色源码/测试/运维区”**结构：

### 2.1 `z-*` 通用标准目录（完全继承个人模板规范并适配团队）

- `z-docs/`：**通用原始设计规格、外部架构文档、API 定义与协议标准（原始需求输入区，只读）**。仅存放用户/甲方提供的原始需求文档、外部参考资料与输入规范，**严禁将新生成的文档写入 `z-docs/`**。
- `z-logs/`：**迭代日志、变更追踪与修改记录**。仅在满足“硬性约束第 1 条（版本日志——仅限用户主动确认 Opt-in）”的规则下创建记录，格式为 `YYYYMMDDHHMM_FeatureName_TestResult.md`。
- `z-readme/`：**关键分步技术指南、团队制度规范与操作手册（How-Tos）**。统一使用中文编写供团队参考；所有新生成的架构设计、业务描述、技术方案、操作手册、分析报告等通用指导文档统一写入 `z-readme/` 并添加 `YYYYMMDDHHMM_` 时间戳前缀（模板内置的 `00~06_*.md` 基准手册除外）。
- `z-prototype/`：**架构原型、线框图、流程图或早期草案实现**。
- `z-resource/`：**静态资源、参考媒体（图片/视频）、二进制文件及外部库发行包**。
- `z-scripts/`：**自动化脚本、开发辅助工具、启动脚本与构建/部署辅助配方**。**所有新创建的脚本必须存放在此目录中**。
- `z-temps/`：**沙盒测试文件、临时日志或短期环境输出**（不纳入长期版本基线）。

### 2.2 根级控制与治理区

- `docs/delivery/`（各角色）：终版交付物（系统总结、用户手册、部署运维手册等）。

- `server/`（`BE` 拥有）：服务端源码、数据库迁移脚本、后端单元与集成测试。
- `web/`、`mobile/`（`FE` 拥有，不含 `web/e2e/`）：Web 前端与移动端源码、前端组件测试。

## 4. 多环境并行工作机制（同工作树 / 同分支或独立 Worktree）

本模板允许在用户判定任务互不相关、或各角色按职责分工协作时，由多个独立的模型环境（AI 会话）在同一项目文件夹及同一分支（或各自 `git worktree`）中并行工作。并行工作采用 `optimistic-disjoint-files`（乐观不相交文件）策略：**允许并发只读，但并发写入必须声明互不重叠的文件所有权（Non-overlapping Ownership）。**

### 4.1 并行配置（Parallel Configuration）

- **配置文件**：`.agents/parallel/config.yaml`。
- **泳道记录（Lane Records）**：`.agents/parallel/lanes/<task-id>-<slug>.md`（团队模式下建议 `<slug>` 包含角色编码，如 `T21-BE.md`）。
- **运行时租约（Runtime Leases）**：`.agents/parallel/leases/<resource>.lock/`。
- **必填声明项**：每一个执行写入操作的环境，必须声明唯一的 `actor_id`、对应的 `role_id`、单一的 `task_id`、精确的拥有路径 `owned_paths`、所需共享资源（Required Resources）、观测到的 Git 分支与 `HEAD` 提交号、涉及的稳定功能范围（Stable-Function Scope）、心跳时间（Heartbeat）、验证方式及回退说明（Rollback Notes）。
- **授权边界**：用户声明“任务相互独立”仅授权并行执行，**绝不代表**授权修改已冻结的稳定功能（`🔒 STABLE`）、执行破坏性操作、执行发布动作或进行重叠路径写入。

### 4.2 所有权与冲突故障处理行为（Ownership & Failure Behavior）

- **读写权限分离**：读取文件不需要声明所有权；**写入文件必须先声明所有权**（且必须符合本角色在 `docs/collab/OWNERS.md` 中的权限范围）。
- **严禁所有权交集**：所有活跃泳道（Active Lanes）绝不能拥有相同的文件、相互重叠的目录、相同的构建生成输出路径或相同的稳定功能代码范围。
- **发现冲突立即停机（Fail-Closed）**：一旦发现路径或范围重叠，必须立即停止对该范围的写入并报告冲突。**严禁**覆盖、回退、丢弃或自动合并其他泳道的工作成果。
- **原子租约获取**：通过原子创建目录（等价于 `mkdir .agents/parallel/leases/<resource>.lock`）来获取共享资源租约；目录创建失败即表示该资源已被其他环境持有。
- **租约元数据与释放**：获取租约后，在锁目录内写入 `owner.md`，记录 `actor_id`、`role_id`、`task_id`、当前分支、获取时间与心跳时间。**每个环境只能释放由当前 `actor_id` 自己持有的租约。**
- **陈旧租约处理铁律**：绝不能仅仅因为租约时间戳看起来陈旧就直接删除锁目录。必须先检查其对应的泳道文件和正在执行的操作；如果无法证明原持有者已正常退出，必须按失败关闭（Fail Closed）处理并询问用户。

### 4.3 共享元数据与任务泳道（Shared Metadata & Task Lanes）

- **`_STATE.md` 是紧凑型并行看板，而非单任务互斥锁**：多个互不关联或不相交的泳道可以同时处于活跃状态（`🔄 IN_PROGRESS`）。
- **`task-metadata` 租约保护范围**：修改 `_TASKLISTS.md`、`_CHECKLISTS.md`、`_STATE.md`、`_STATE_HISTORY.md`、`AGENTS.md`、`.agents/parallel/config.yaml`（以及团队全局计划 `docs/PLAN.md`、`docs/PROGRESS.md`、`docs/collab/OWNERS.md`）前，**必须先获取 `task-metadata` 租约，并在获取租约后立即重新读取文件最新内容**，方可编辑。修改协作看板 `docs/collab/BOARD.md` 须先获取 `collab-board` 租约并重读。
- **详细进度与共享摘要分离**：详细的实时执行进度记录在各自的 `.agents/parallel/lanes/<task-id>-<slug>.md` 泳道文件中；共享控制文件仅记录简明的里程碑、审批状态、验收结果与归档摘要。
- **新任务优先级局部性**：用户下达的新任务仅在接收该任务的当前环境中成为最高优先级；除非用户明确指令暂停或替换另一个具名泳道，否则**严禁自动驱逐或中断其他不相关的活跃泳道**。
- **跨泳道操作禁令**：任何一个环境均不得擅自暂停、完成、重新指派其他泳道的任务，也不得替其他泳道的任务确认用户验收。

### 4.4 共享工作树中的 Git 安全规范（Git Safety in a Shared Worktree）

- **并行工作区编辑的前提**：工作区文件编辑与只读 Git 命令（如 `git status`、`git diff`、`git log`）仅在互不相交的 `owned_paths` 范围内才允许并行执行。
- **Git 写操作强制获取 `git-index` 租约**：在执行 `git add`、`git commit`、`git commit --amend`、`git merge`、`git rebase`、`git cherry-pick`、`git tag`、分支切换（`git checkout` / `git switch`）、`git pull` 或 `git push` 等任何改变 Git 索引或引用状态的命令前，**必须先获取全局 `git-index` 租约（`.agents/parallel/leases/git-index.lock/`）**。
- **暂存前复核 `HEAD` 变化**：在开始任务时记录起始 `HEAD`；在即将执行暂存（Staging）之前，必须重新读取当前的 `HEAD`、`git status` 及已变更文件路径。如果期间有其他泳道完成了提交，必须核实这些中间提交没有触碰当前泳道的 `owned_paths`。
- **仅允许显式路径暂存**：必须且只能暂存当前泳道明确拥有的路径：`git add -- <paths>`。在并行模式下，**严禁使用 `git add -A`、`git add .`、`git commit -a`、共享 `git stash` 以及任何不带显式路径的批量暂存命令**。
- **核验暂存区子集**：执行提交前必须检查 `git diff --cached --name-only`，确保暂存区中的所有文件严格属于当前泳道 `owned_paths` 的子集。如果暂存区（Index）中已存在其他泳道的文件路径，**严禁擅自取消暂存（Unstage）或修改它们**，必须与该路径的拥有者协调处理。
- **单泳道原子提交与回滚禁令**：每一次 Git 提交（Commit）只能包含单一泳道的修改，且提交信息应包含任务 ID（及角色编码）。**严禁**使用 `git reset`、`git restore` / `git checkout --`、`git clean`、`git revert`、`git rebase`、`git commit --amend` 或 `git stash` 来处理并行冲突或干扰。
- **同文件或分叉历史处理**：如果多个任务必须编辑同一个文件，或者需要分叉的提交历史（Divergent History），必须将它们串行化执行，或使用独立的 `git worktree` / 独立分支。

### 4.5 构建、产物输出与外部资源（Builds, Outputs & External Resources）

- **构建隔离与构建租约**：并行构建必须使用各自独立的构建/输出目录；若共用同一个构建目录树，则必须先获取对应的构建租约（如 `build`、`backend-build`、`frontend-build`）。
- **打包与镜像输出**：日常打包应使用泳道专属的输出路径；生成标准发布产物或镜像时，必须获取 `image-output` 租约。
- **目标设备与环境操作租约**：执行服务部署、进程重启、系统重启、断电/上电循环（Power Cycle）、串口抓取、固件/环境变量写入、烧录（Flashing）以及 OTA 安装时，必须先获取 `target-device`（或对应 `test-env`、`staging-env`）及相关子资源租约，严格串行执行。
- **硬件/物理验证挂起局部性**：因等待用户物理/硬件验证而产生的暂停仅针对当前泳道生效，不阻塞其他不相关的活跃泳道。

## 5. 任务状态跟踪与并行领取模式（Task State Tracking & Parallel Lane Claiming）

根目录使用四个固定名称的共享控制文件和独立的泳道（Lane）文件协同管理任务生命周期：

- `_STATE.md`：紧凑并行看板，可同时显示多个活跃泳道（Lane）及当前项目阶段。
- `_TASKLISTS.md`：保存全部任务、优先级、依赖关系、完成标准和泳道/角色归属。
- `_STATE_HISTORY.md`：以追加（Append-only）方式保存已完成或已取消的任务归档记录。
- `_CHECKLISTS.md`：保存已验收稳定功能（`🔒 STABLE`）清单、冻结代码范围和跨功能交叉影响。
- `.agents/parallel/lanes/`：保存各工作环境/角色的详细实时进度、文件所有权（`owned_paths`）和资源需求。

### 强制执行规则

#### 5.1 任务来源与并行语义

- 任务只能由用户发布，或为完成用户任务而拆解的必要子任务（团队模式下由 `PM` 登记拆解至 `_TASKLISTS.md` 与 `docs/PLAN.md`）。
- 当用户判定任务互不相关（或不同角色负责互不重叠模块）时，多个泳道可在同一目录和同一分支（或各自专用分支）上同时处于 `🔄 IN_PROGRESS` 状态。
- 新任务只在接收它的泳道中成为最高优先级；未经用户明确指定，不得暂停或替换其他不相关泳道。
- 并行执行不扩大稳定功能修改、破坏性操作、正式发布、硬件验收或生产变更的授权范围。

#### 5.2 会话启动与泳道领取（Session Startup & Lane Claiming）

- 每次会话启动时，必须先读取 `AGENTS.md`、`.agents/parallel/config.yaml`、`_STATE.md`、`_TASKLISTS.md`、`_CHECKLISTS.md`（以及团队模式下的 `.agents/roles/<ROLE>.md`、`docs/collab/OWNERS.md`、`docs/collab/BOARD.md`）和当前所有活跃泳道摘要。
- 有新任务时，先获取 `task-metadata` 租约，登记任务并创建唯一泳道文件 `.agents/parallel/lanes/<task-id>-<slug>.md`。
- 明确声明 `actor_id`、`role_id`、`task_id`、当前分支/`HEAD`、`owned_paths`、所需资源、稳定功能范围、心跳时间、验证方案和回退方案。
- 领取前比较所有活跃泳道：文件所有权和资源无重叠方可并行；若存在重叠则按失败关闭（Fail Closed）停机并报告。
- 无新任务时，只自动领取依赖已满足、尚未被领取、符合当前角色职责且与活跃泳道无冲突的最高优先级任务。

#### 5.3 执行与共享文件维护

- 每个环境只允许修改自己 `owned_paths` 范围内的文件。一旦发现重叠立即停止写入，保留现状并向用户报告，严禁覆盖、回退或自动合并。
- 详细的实时执行进度写入各自的泳道文件；共享状态文件只写入必要的里程碑节点。
- 修改 `_STATE.md`、`_TASKLISTS.md`、`_CHECKLISTS.md`、`_STATE_HISTORY.md`、`AGENTS.md` 或并行配置文件前，必须先获取 `task-metadata` 租约并立即重新读取文件最新内容。
- 某个泳道在等待用户确认、跨角色答复或硬件验证时，不阻塞其他无关泳道继续推进。

#### 5.4 Git、构建与外部资源协同

- Git 写操作必须先获取 `git-index` 租约，仅显式暂存自有路径（`git add -- <paths>`），一次提交仅对应一个泳道，并在暂存前复核期间 `HEAD` 的变化。
- 严禁使用 `git add -A`、`git add .`、`git commit -a`、共享 `stash` 和无路径批量暂存。当暂存区索引中出现他人路径时，不得擅自取消暂存。
- 构建/输出目录重叠时必须获取对应构建租约并串行执行；只有独立输出目录才允许并行构建。
- 部署、进程重启、断上电、串口采集、固件/环境写入、烧录和 OTA 安装必须按 `target-device`（及 `test-env` / `staging-env`）对应子资源租约串行执行。

#### 5.5 完成与归档（Completion & Archiving）

- 内部验证（自检、单测或跨角色联调测试）完成后，只能将状态标记为 `🧪 AWAITING_USER_CONFIRMATION`；**只有当用户明确回复“通过”、“稳定”、“完成”或“验收通过”后，才允许标记为 `✅ COMPLETED`**。
- 用户下达新任务绝不代表旧泳道已默认验收通过，也不自动暂停旧泳道。
- 用户反馈验证失败时，只将对应泳道恢复为 `🔄 IN_PROGRESS` 继续修复。
- 用户验收通过后，获取 `task-metadata` 租约，同步更新 `_STATE.md`、`_TASKLISTS.md` 与 `_STATE_HISTORY.md`，将该泳道标记完成并释放其持有的全部租约。

#### 5.6 任务状态流转图

```text
⏳ TODO → 泳道(Lane)领取 → 🔄 IN_PROGRESS → 🧪 AWAITING_USER_CONFIRMATION
                              ├→ 用户明确通过 → ✅ COMPLETED → 追加归档至 _STATE_HISTORY.md
                              ├→ 用户反馈失败 → 🔄 IN_PROGRESS
                              ├→ 文件/资源冲突 → ❌ BLOCKED（仅该泳道/范围）
                              ├→ ⏸️ PAUSED → 条件解除后恢复
                              └→ 🚫 CANCELLED → 追加归档至 _STATE_HISTORY.md

注：多个文件与资源无重叠的泳道（Lane）可同时处于 🔄 IN_PROGRESS。
```

## 6. 稳定功能冻结与功能核对清单（Stable Function Freeze & Feature Checklist — Mandatory）

- **`_CHECKLISTS.md` 是项目的权威功能清单**：在开始任何新功能开发、缺陷修复、代码重构、性能调优或平台适配任务之前，必须先读取 `_CHECKLISTS.md`，识别目标功能、已登记的代码范围、当前状态以及跨功能交叉影响（Cross-Feature Effects）。
- **严禁破坏已稳定功能**：在实现新需求或修复缺陷时，**绝不可**修改、削弱、移除或破坏任何已标记为 `🔒 STABLE` 的现有功能。必须优先采用隔离式新增和最小化变更策略，并在完成后对列出的所有受交叉影响的功能执行完整回归测试。
- **`🔒 STABLE` 认定的唯一标准**：一项功能**只有在开发者或用户亲自测试并明确声明其稳定后**，才允许标记为 `🔒 STABLE`。仅有代码存在、编译成功、自动化测试通过或 AI 代理自行判断，均不足以将其升级为 `🔒 STABLE`。
- **稳定代码范围冻结与变更汇报门禁**：一旦某功能被标记为 `🔒 STABLE`，其登记的代码范围即处于冻结状态。如果确实有必要修改该范围内的代码，**必须在编辑任何文件之前立即暂停**，向用户清晰报告：目标功能名称、精确代码范围、修改原因、受影响的关联功能、回归测试计划以及回退计划。
- **获批后状态切换与实施**：只有在获得用户明确批准后，才允许修改稳定代码。修改前必须先在 `_CHECKLISTS.md` 中将其状态更改为 `⚠️ CHANGE_APPROVED` 或 `🔄 REVALIDATING`，记录批准信息与修改范围，然后再执行经批准的代码修改。
- **回归验证与状态恢复**：修改完成后，必须对原稳定功能及所有受交叉影响的功能进行全面回归测试。**只有当开发者或用户明确验收通过新的结果后**，才允许将其状态恢复为 `🔒 STABLE`。
- **保持实时同步**：每当新增、修改、测试、验收通过、禁用或替代任何功能时，必须同步更新 `_CHECKLISTS.md`。

## 7. 团队跨角色协作五大闭环协议（Team Collaboration Closed-Loop Protocols）

在遵守上述 Git 版本控制、并行泳道与稳定冻结规范的基础上，团队各角色之间通过 `docs/collab/` 下的标准单据进行异步协同（详见 `z-readme/03_项目沟通任务流转与接口对接规范.md`）：

1. **阶段门禁闭环（P0 立项 → P1 需求 → P2 架构契约 → P3 底座脚手架 → P4 迭代开发 → P5 独立测试 → P6 预发与生产发布 → P7 验收归档）**：上游阶段出口门禁（含架构评审单 `RV`）未通过前，下游角色不得提前进入正式编码或发布。
2. **契约先行与变更分级闭环（`AR` / `BE` / `FE` / `QA`）**：接口实现前必须先冻结 `docs/design/api/OPENAPI.yaml`。兼容扩充（L1）更新契约并发交接单 `HO`；破坏性变更（L2，删改字段/路径/状态码）必须发起变更单 `CR`，经 `AR`、`FE`、`QA` 评估与 `PM` 批准后方可执行。
3. **跨角色阻塞提问闭环（`/ask` ↔ `/answer`）**：发现上游文档模糊、契约缺失或他人代码问题时，**严禁越权代改他人文件或私自猜测**，必须在 `docs/collab/issues/` 创建问题单 `IS-YYYYMMDD-NNN` 指派给责任角色，由责任角色修复并回复 `/answer`。
4. **测试准入、缺陷流转与准出闭环（`BE/FE` ↔ `OPS` ↔ `QA`）**：代码合入 `develop` 并由 `OPS` 部署至 `test` 环境（附 Git Commit SHA）后，`QA` 执行测试；发现 Bug 提报缺陷单 `/defect`（`IS-xxx`）→ 开发先补失败单测再修复，状态改 `待复测`（**严禁开发自行关闭缺陷单**）→ `QA` 执行 `/retest` 验证通过后关闭缺陷 → 全部 P0/P1 清零后由 `QA` 出具 `/gate` 准出报告。
5. **生产发布与业务验收闭环（`OPS` ↔ `PO` ↔ `PM`）**：`OPS` 完成预发布部署、健康检查与回滚演练（`/deployed`）→ `PO` 对照 `ACCEPTANCE-CRITERIA.md` 逐条执行 `/accept` 业务验收 → 用户确认通过后由 `PM` 汇总归档并合并入 `main`。

## 8. 硬性工程约束（Hard Constraints — Must Follow）

1. **版本日志——仅限用户主动确认（VERSION LOGGING — USER OPT-IN ONLY）**：日常代码实现、缺陷修复、重构、配置修改、编译构建和普通功能改进，**严禁**自动在 `z-logs/`、`z-readme/` 或其他任何位置创建修改记录或技术文档。只有当变更属于重大架构调整、重要里程碑或大规模功能完成时，记录才有意义；在创建之前，**必须先明确询问用户是否需要生成修改记录技术文档**。只有在用户明确确认后（或用户在一开始就明确要求生成该文档时）才允许创建。提问与生成的文档均须保持简明扼要以节省 Token。若用户确认生成，须将详细验证记录以 `YYYYMMDDHHMM_FeatureName_TestResult.md` 格式保存在 `z-logs/` 中，并在文内包含具体的验证日期与时间。
2. **中文技术文档规范（CHINESE DOCUMENTATION）**：关键的分步技术指南存放在 `z-readme/` 中且必须使用中文编写，但日常普通代码工作严禁自动创建。仅在用户明确要求、或在满足上述第 1 条重大变更询问并获用户确认后才允许创建。**所有新生成的通用技术文档统一写入 `z-readme/` 文件夹**（包括架构设计、业务描述、技术方案、操作手册、分析报告等，统一使用中文并添加 `YYYYMMDDHHMM_` 时间戳前缀）；**`z-docs/` 仅作为原始需求文档使用**（存放用户提供的原始需求、外部参考资料与输入规范，严禁将新生成的文档写入 `z-docs/`）。
3. **Markdown 表格列对齐（MARKDOWN TABLE FORMAT）**：生成或修改的所有 Markdown 文件中的每一个表格，**必须严格保持列对齐（Column-Aligned）**。同一表格中的每一行必须具有相同的可见列宽（中文字符按 2 个英文字符宽度计算），在竖线分隔符 `|` 前后填充空格，确保在纯文本源码视图下所有 `|` 垂直对齐（可运行 `py -3.11 z-scripts/validate_project.py --align` 校验并自动对齐）。
4. **脚本存放位置（SCRIPT PLACEMENT）**：任何新创建的 Shell 脚本（`.sh`）、PowerShell 脚本（`.ps1`）、Python 辅助脚本（`.py`）或自动化运行器，**必须统一存放在 `z-scripts/` 目录中**（容器与生产部署专用脚本存放在 `deploy/scripts/`）。
5. **不确定关键操作必须先确认（UNSURE CRITICAL OPERATIONS）**：如果你不确定某项操作是否属于关键、核心或高风险操作，**必须立即停止并在继续执行前向用户询问确认**。
6. **Git 版本控制安全（GIT VERSION CONTROL）**：未经用户事先明确批准，**绝不执行** `git reset`、`git checkout -- <file>`、`git restore`、`git revert`、`git clean` 或任何形式的代码回滚/丢弃操作。如果确实需要回滚，必须先向用户解释原因并等待批准。
7. **绕过冗余规划模式（PLANNING MODE）**：忽略/绕过工具内置的形式化 Planning Mode。除非用户明确要求，或正在执行大规模架构重写（或按本团队模板角色职责编写 `docs/PLAN.md`），否则不要生成临时的 `implementation_plan.md` 阻塞等待确认，应直接开展代码分析与任务实现。
8. **物理/硬件/界面验证门禁暂停（PAUSE FOR PHYSICAL/HARDWARE VERIFICATION）**：每当验证工作需要检查显示质量、触控反馈、音频输出、界面视觉效果或物理/硬件交互时，**必须立即暂停**，向用户说明当前状态与验证要点，并等待用户完成物理/实机验证反馈后再继续执行。
9. **文档时间戳命名规则（DOCUMENT NAMING）**：所有新生成的文档（代码源文件、执行脚本、四个固定根级控制文件 `_STATE.md` / `_TASKLISTS.md` / `_STATE_HISTORY.md` / `_CHECKLISTS.md`、`AGENTS.md`、模板内置编号手册 `z-readme/00~06_*.md` 及 `docs/` 下按规范命名的固定工程产物除外）**必须在文件名前添加精确到分钟的 `YYYYMMDDHHMM` 时间戳前缀**（例如 `202606171446_FileName.md`），以便按时间排序。四个根级控制文件 `_STATE.md`、`_TASKLISTS.md`、`_STATE_HISTORY.md` 和 `_CHECKLISTS.md` 是明确的例外，必须保持完全一致的原名。
10. **深度问题分析与需求探问协议（DEEP PROBLEM ANALYSIS & INQUIRY PROTOCOL）**：当处理开放式技术咨询、方案选型设计或需求边界模糊的任务时，必须严格遵循下方第 9 节《深度问题分析与需求探问协议》：挖掘未言明的隐性假设、分析缺失信息的决策敏感度、指出最常犯的一个典型错误，并在给出最终方案前**仅提出唯一一个最关键的问题**等待用户答复。

## 9. 深度问题分析与需求探问协议 (Deep Problem Analysis & Inquiry Protocol)

本协议是 Agent 在面对用户提出的技术咨询、方案选型、架构设计、复杂疑难排查以及边界模糊的新需求时的核心思维模型与交互规范。其核心宗旨是：**拒绝盲目猜测、拒绝平庸套话、打破隐藏假设、通过精准门禁探明真实目标，实现靶向定制交付。**

### 9.1 适用场景与触发条件

- **必须触发**：
  1. 用户进行技术选型、架构设计、方案咨询或寻求疑难问题解决思路时；
  2. 用户需求仅给出了方向或粗粒度目标，缺乏具体上下文与硬性边界约束时；
  3. 用户的提问可能蕴含认知偏差、底层假设冲突或隐藏工程风险时；
  4. 用户明确要求按此协议进行深度分析与探问时。
- **免除触发**：
  - 上下文充分、规格明确的机械性代码修改、单纯语法报错修复、明确命令执行等日常确定性任务，直接执行，不增加沟通摩擦。

### 9.2 交互三阶段执行流程

```text
用户提出问题 / 咨询 / 模糊需求
       │
       ▼
【阶段一：三维解构与关键追问】（严禁直接给最终方案或套用通用模板）
  ├─ 1. 挖掘隐性成立的假设 (Tacit Assumptions)
  ├─ 2. 识别缺失信息及决策敏感度 (Information Gap & Sensitivity)
  └─ 3. 预警高频认知与工程误区 (Common Anti-Patterns)
  │
  └─► 提炼并抛出【唯一最关键的核心问题】 (Single Critical Question)
       │
       ▼
【阶段二：门禁暂停与等待反馈】(Gating: Pause & Wait)
  - 严禁提前给出最终方案/通用建议，严禁罗列漫长问题清单
  - 挂起等待用户针对该核心问题的具体答复
       │
       ▼
用户完成针对性答复
       │
       ▼
【阶段三：靶向交付与落地解答】(Targeted Final Output)
  - 基于真实目标与约束，提供深度定制、一针见血的最终方案
```

### 9.3 分析要素细则与标准

在输出第一阶段分析时，必须严格执行以下四项规范：

#### (1) 挖掘隐性假设 (Unstated Tacit Assumptions)
- **要求**：深入剖析提问表面背后的预设前提，指出用户在问题中未明确表述、但潜意识中已默认成立的假设。
- **分析维度**：
  - **技术与架构假设**：是否默认了特定的编程语言、运行时版本、框架生态或网络拓扑？
  - **硬件与性能假设**：是否默认了充足的算力/内存/带宽？还是受限于嵌入式低功耗环境？
  - **业务与生命周期假设**：是否默认了业务规模（单机 vs 分布式）、开发周期、预算成本或团队技术栈？
  - **质量与容错假设**：是否默认了系统高可用、数据绝对一致，还是允许弱一致与短暂降级？

#### (2) 明确缺失关键信息及敏感度评估 (Information Gaps & Sensitivity Analysis)
- **要求**：不仅要列出缺少哪些关键信息，**更必须详细推演这些信息将如何决定性地改变最终答案**。
- **范式**：“当前缺少 [信息X]。如果 [情况A]，最佳方案应为 [路线1]；但如果 [情况B]，方案则完全颠覆为 [路线2]。”
- **原则**：拒绝空泛地罗列无意义清单，重点突出信息对决策走向的因果杠杆作用。

#### (3) 指出最常犯的一个典型错误 (Single Most Common Anti-Pattern)
- **要求**：精准提炼行业内或工程师在处理此类问题时**最容易陷入的一个核心误区**。
- **类型**：如“错把手段当目标”、“过早进行性能优化”、“混淆逻辑隔离与物理隔离”、“忽视特定平台的硬件/系统限制”、“直接套用通用Web架构到嵌入式环境”等。
- **作用**：帮助用户提前避坑，提高思考维度与决策成熟度。

#### (4) 提出单一最关键问题 (Single Critical Hinge Question)
- **黄金法则**：**只提一个问题！坚决禁止抛出多个并列问题或问题清单。**
- **选拔标准**：
  - 这个问题必须是解开整体方案死锁的“第一推动力”或“阿基米德支点”；
  - 能够最大程度揭示用户的**真实业务目标、绝对核心约束或关键妥协边界**；
  - 一旦此问题明确，后续的技术选型与实现细节将顺理成章、豁然开朗。

### 9.4 规范对照表

| 核心维度              | 执行目标         | 执行标准与硬性禁忌                                       |
| :-------------------- | :--------------- | :------------------------------------------------------- |
| **1. 挖掘隐性假设**   | 破除认知盲区     | 识别未言明的技术、硬件、业务预设前提，防范隐藏风险       |
| **2. 缺失信息推演**   | 评估决策敏感度   | 明确不同条件输入如何颠覆最终架构与技术路线               |
| **3. 常见误区预警**   | 规避高频踩坑     | 精准指出业内同行处理此类问题最常犯的 1 个核心错误        |
| **4. 单一杠杆追问**   | 锁定核心真实目标 | 严禁列问题清单，仅提 1 个决定性的阿基米德支点问题        |
| **5. 门禁与靶向交付** | 确保最终方案可用 | 必须等待用户明确答复后，再输出深度定制方案，杜绝通用套话 |

### 9.5 门禁与交付规范

- **禁止抢答**：在用户回答该核心问题之前，坚决禁止提前附带“如果不确定，建议你……”之类的泛化兜底结论。
- **精准交付**：用户回复后，立刻聚焦其具体答复进行最终方案构建，确保方案具有极高的场景贴合度与直接可落地性，杜绝空洞模板与泛泛而谈。

## 10. 命令执行安全规范（Command Execution Safety）

### 10.1 ⚠️ 全局绝对例外（Global Exception）
- **任何包含 `rm -rf` 的命令无论在何种情况下都必须始终先获得用户明确确认**，不受下方任何自动运行规则的豁免。

### 10.2 允许自动安全运行（SafeToAutoRun = true，无需确认）
- 在 Windows（PowerShell / CMD）和 WSL（Ubuntu）上的**所有常规命令**默认允许自动执行，**但下方第 10.3 节列出的受阻断（BLOCKED）命令除外**。
- 允许自动运行的非破坏性操作包括：本地工作区搜索（`grep`、`rg`）、通过本地 Makefile 进行常规代码编译（`make`）、日志读取、安全文件传输（`pscp`、`scp`）、Git 与进程状态检查（`git log`、`git diff`、`git status`、`ps`）以及短暂延时等待（`Start-Sleep`）。

### 10.3 受阻断的高危命令（BLOCKED — 必须先获用户确认）
- **破坏性文件系统操作**：`rm`、`del`、`Remove-Item`、`mv`、`move`、`ren`、`Rename-Item`（在执行删除、重命名或移动前，必须先备份为 `filename.bak.YYYYMMDDhhmmss`，向用户展示操作计划并等待确认）。
- **系统或磁盘变更操作**：`format`、`fdisk`、`dd`、`mkfs`。
- **数据库结构或高危数据变更**：`DROP DATABASE`、`DROP TABLE`、`truncate`。
- **系统控制与网络变更**：`iptables -F`、`shutdown`、`reboot`、`poweroff`。
- **强制终止进程与服务**：`kill -9`、`systemctl stop`。
- **高风险 Git 操作**：`git push --force`、`git reset --hard`。
- **生产环境数据变更**：任何触及生产环境（Production）、线上活跃数据库或生产发布流的变更操作。
- **复杂重型目标平台编译**：Android 原生构建（例如 `gradlew.bat` / `gradlew assembleDebug`、`assembleRelease`）、Qt 项目编译（例如 `qmake`、`mingw32-make`、`nmake`、`jom`）。
