# AGENTS.md —— 多用户、多角色 AI 软件团队协作规则

适用于复制后的独立 Git 项目。角色卡负责专业职责，本文负责身份、写入边界、冻结与 Git 流程。旧提示词中的简写不得覆盖本文；用户已经明确授权的事项不重复请求确认。敏感信息在写入任何仓库文件前脱敏，使用 `***`、公开示例域名或变量名。

## 1. 身份与工作入口

每个写入会话声明五项身份：

- `user_id`：稳定的人员标识；同一个人切换会话不变。
- `actor_id`：当前执行会话标识，不得借用他人的标识。
- `role_id`：本会话的专业角色（PM、PO、AR、BE、FE、QA、OPS、AI）。
- `task_id`：被授权的任务编号；`lane_id`：唯一任务泳道编号。
- 推荐泳道 `T021-BE-dev01-s01`，分支 `feature/T021-be-dev01-s01`。同角色允许任意多名用户，角色不是锁的键。

启动时先运行 `git rev-parse --show-toplevel`、`git symbolic-ref --short HEAD`、`git status --short`，核实实际项目与现有改动。再阅读本文、角色卡、`_STATE.md`、`_TASKLISTS.md`、`_CHECKLISTS.md`、`.agents/parallel/policy.json` 及协调中心状态。没有新任务时，只领取已授权且依赖满足的任务；不得自动替换其他人的任务。

默认一人一任务一分支一工作树；同一工作树只允许一个写会话。独立工作树仍要检查文件与功能边界。技术角色按模块、文件及资源细分，不能因为同为 BE 就各自占用整个 `server/`。只读评审会话不领取写锁、不写文件。

## 2. 目录与职责

所有新生成的工程文档、会议记录、交接单、泳道记录、审批与验证报告放入 `z-readme/`，用中文编写，文件名带 `YYYYMMDDHHMM_` 前缀；建议再包含任务、角色、人员标识，避免同分钟重名。既有 `AGENTS.md`、四个根控制文件、角色卡与工作流入口保持固定名字以供工具读取。新增文档不在这些控制目录扩散。

`z-docs/` 只存用户原始输入，AI 不修改。旧 `docs/` 工程模板已迁入 `z-readme/`，实际文件见工程文档导航。代码保留正常工程文件名；可执行契约、SQL 与 Schema 是工程输入，可按工具要求保留稳定文件名。辅助脚本统一放 `z-scripts/`。临时输出用各泳道独立的 `z-temps/<lane>/`；不把秘密放入临时目录来规避脱敏。

- PM：计划、分派、看板、资源与阶段统筹。
- PO：需求、规则、验收标准与业务验收。
- AR：架构、技术约束、所有权策略和技术评审。
- BE：`server/`、数据库与接口设计。
- FE：`web/`、`mobile/`；其中 `web/e2e/` 归 QA。
- QA：`tests/`、`web/e2e/`、独立测试及缺陷关闭。
- OPS：`deploy/`、`.ci/`、平台流水线与环境。
- AI：`ai/`、模型应用设计与评测。

机器校验按 `.agents/parallel/policy.json` 的最具体路径规则执行；广目录包含其他角色子目录时必须拆分领取。评审矩阵见 `z-readme/collab/202611122304_文件归属与评审矩阵.md`。专业角色是默认权限；真人批准的窄范围跨角色接手可以覆盖默认写入角色，不要求原角色操作，但不能让修复者同时替代独立 QA/业务验收。

## 3. 三类约束分别维护

1. **职责归属**：谁通常负责某类工作，由角色矩阵说明。
2. **运行写锁**：谁此刻可以改哪些文件、构建目录、数据库迁移或环境，由唯一协调中心维护。
3. **成果冻结**：某个已交付版本不得再被改动，包含文档、代码、测试、配置与契约，由产出责任人登记；写锁释放后冻结继续存在。

不得把上述三者混成一个角色锁，也不得把“冻结”当作“验收稳定”。交付冻结状态为 `FROZEN`；只有真人确认验收后才在 `_CHECKLISTS.md` 标为 `STABLE`。自测通过、合并成功、部署成功均不自动代表 STABLE。

### 3.1 领取、互斥与回收

使用 Python 3.10+（推荐 3.11）运行 `z-scripts/team_guard.py`。同一 Git 仓库的 worktree 默认通过 `git rev-parse --git-common-dir` 定位共享协调中心，不能各自在 `.agents/parallel/leases/` 建锁。原来的 Markdown 泳道摘要不是锁，Git 版本文件也不是分布式互斥原语。

`claim` 在同一原子事务中检查并写入路径及资源占用。父子目录、大小写别名、同文件、同资源不能同时领取；禁止路径穿越、通配符及符号链接。目录以 `/` 结尾。心跳用 `heartbeat`；超时只用于排查，绝不自动解锁。

冻结的范围必须先获批，才能领取。共享元数据要求 `task-metadata` 资源；数据库迁移编号、测试环境、设备与共享构建输出分别声明资源。构建优先使用独立输出目录、端口和数据库 schema。

正常 `release` 仅由当前 actor 操作。持有者失联时，真人可以批准 `recover`：记录当前泳道摘要、原进程停止证据和未提交工作保全位置，任意被指定人员执行；无需原角色返回。回收写锁不会解冻成果。事务锁因崩溃残留时同样由维护者确认无活跃进程、备份状态、留存人工记录后处理；工具不按时间猜测。

### 3.2 成果冻结

每名用户对自己生成的文档、源码及相关工程产物负责，在评审/交接前完成自检与显式提交，再执行 `freeze`。记录冻结编号、所有者 user/actor/role、任务、精确文件或目录、提交 SHA、文件模式与 SHA-256 摘要、自检证据及版本。

冻结登记写入统一协调中心；交接时导出带时间戳的审计快照纳入 Git。原作者、新成员、其他角色、格式化工具、重命名和删除都受同一冻结限制。冻结不因会话结束、租约释放、人员离职或重新克隆而失效。

### 3.3 人工解冻与接手

发现明确的接口或功能干涉时，先形成 CR：列出冻结编号/版本、问题依据、最小改动范围、受影响功能、回归与回退计划、指定接手的 user/actor/role/task、有效期。**在获得真人明确批准前不得编辑冻结文件。** 原作者也适用。普通“优化一下”、静默、超时、AI 自审以及角色为 PM/AR 均不等于批准。

可直接依据本次会话已存在的明确批准登记，不重复询问。批准可以交给其他角色/用户执行，无须原作者签字或操作；必须保留独立评审与回归。L1 兼容接口变化和 L2 破坏性变化都不能豁免冻结解锁。

状态流：`FROZEN → CHANGE_APPROVED → 修改与回归 → FROZEN（新版本）`。未完成重新冻结不能静默释放泳道。批准绑定旧提交与版本，禁止重放；到期、对象改变或超范围均停止对应范围。续批须再次获得真人确认，并用 `supersedes` 明确替代旧批准。取消变更也须核验回到批准基线，再重新冻结；不自动回滚代码。

`team_guard.py thaw` 只校验批准记录的结构、范围、版本与期限，**不能认证真人身份**。执行者只能转录真实批准，不能自行造审批。正式项目应把批准记录、策略及工具变更纳入受保护 PR，审批权限与开发权限分开。

## 4. Git 提交与合并

### 4.1 开发提交

- `main`/`master` 为发布基线，`develop` 为受保护集成线，均不直接开发。
- 从已知 SHA 创建 `feature/<TASK>-<ROLE>-<USER>-<SESSION>` 或 `fix/...`，每人独立 worktree。新仓库仅在尚无协作者的引导阶段创建初始基线。
- 一个提交只含一个任务泳道。仅 `git add -- <明确自有文件>`；禁止 `git add .`、`git add -A`、`git commit -a`、共享 stash、擅自取消他人暂存。
- 暂存前复核 HEAD、工作树与暂存区；执行 `team_guard.py check --lane ... --actor ... --staged`，再检查 `git diff --cached`。
- 提交信息统一为 `[<ROLE>][<TASK>][<USER>] <type>: <中文说明>`，例如 `[BE][T021][dev01] feat: 实现订单查询`。
- 交接前使用 `check --base <精确基线SHA>` 检查完整提交差异，再自检、冻结并提 PR。禁止把 `HEAD` 作为假基线来掩盖变更。

各 worktree 有独立 index 与 HEAD，正常 add/commit 不必被一个全仓 `git-index` 锁串行阻塞。引用、工作树创建、集成线更新、标签和发布由指定集成人员串行管理。若只能使用同目录，所有写会话串行，不支持旧版的同目录多写者例外。[Git worktree 官方说明](https://git-scm.com/docs/git-worktree)

### 4.2 有序集成

1. PR 写清任务、提交 SHA、冻结编号、改动路径、依赖 PR、接口影响、人工解冻记录及测试证据。先合契约/公共基础，再合消费者；互不依赖的 PR 可并行评审。
2. 由团队指定的集成人员管理合并队列。记录目标旧 SHA、源 SHA 和候选合并 SHA。在独立集成 worktree 从目标旧 SHA 合并一个队首 PR，产生真实候选提交。
3. 对**候选合并后的完整文件树**执行构建、单测、契约检查、集成/回归与需要的人工验收；源分支自测不替代此步骤。评审人核对冻结清单，确认所有变化都有对应批准。
4. 文本冲突以及接口、数据库迁移、业务语义冲突必须显式处理。合并冲突若需要改变冻结成果，走人工解冻；可指定任意适合的接手者，无须原角色。冲突修复产生新候选，并重新验证。
5. 目标仍等于记录的旧 SHA 时，只允许将目标快进到验证过的候选提交。目标已前进则重新构造候选、重新验证。禁止合并后补格式化、偷带改动或拿旧测试结果放行。
6. `main` 合并、推送/发布与生产操作按用户授权执行，验收批准绑定实际候选 SHA。若采用平台 merge queue，CI 要检查队列产生的候选，而非只测源 PR。[GitHub merge queue 官方说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)

保护 main/develop：必须 PR、独立评审、必需检查，限制直接推送、删除和强推，变更后旧批准失效；CODEOWNERS 只负责评审路由，不是路径写锁，也不能证明多角色全部签字。[受保护分支官方说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

## 5. 跨机器与工具的边界

`AGENTS.md` 是行为约定，不是文件系统 ACL。Python 工具是遵守约定的参与者使用的本地协调与预检工具，无法阻止直接改文件、绕过脚本或伪造身份。

同机 worktree 自动共享协调中心。独立 clone、不同电脑、CI runner **不会**自动共享 `.git` 内状态。多机器必须显式指向同一受控 `--coord-dir`，并事先验证共享文件系统的原子 mkdir/replace 语义及读写权限；未经验证的网盘同步目录不可用。若网络共享不可用，团队须部署统一协调服务或由单一协调员串行批准路径领取；未落实统一权威时不能宣称全局互斥，也不能各自 init 成独立中心后并行。

协调目录不是生成文档存放处，不提交绝对机器路径或凭据。灾难恢复应停写、核验最新版已审核快照及 Git 提交后导入。历史快照不允许覆盖活跃中心；init 仅用于真正新项目或获人工批准的迁移。策略变更须停写迁移并保留冻结，不能删除状态后重新 init。

## 6. 协作与质量闭环

阶段统一为 P0 启动、P1 需求、P2 架构、P3 详细设计、P4 开发计划、P5 迭代开发、P6 系统测试与发布、P7 交付。

问题用 IS、评审用 RV、交接用 HO、受控变更用 CR。单据含任务与人员身份及精确版本；同角色多人不能共享递增编号而不协调，建议 `<类型>-<TASK>-<USER>-<SESSION>-<序号>`。已冻结单据的答复、评审或签收用新文档引用原编号，不回写冻结原文。共享看板由领取该文件的人汇总。

QA 只测试可追溯提交；修复者不能自行关闭 QA 缺陷。任务执行完标记 `AWAITING_REVIEW` / `AWAITING_TEST` / `AWAITING_USER_CONFIRMATION`；真人确认后归档。等待只影响相关泳道。STABLE 的修改与恢复按 `_CHECKLISTS.md` 记录，不冒充实机、业务或生产验收。

格式化也是写操作。`validate_project.py` 默认只读；`--align --files <已领取文件>` 只处理显式文件，不全仓改写。执行前后遵守同一写锁与冻结检查。

只有缺失信息确实阻塞实现时才请求澄清；已授权、可逆且必要的工作继续推进。禁止通过猜测完成审批、通过删除他人改动解决冲突或未经授权实施生产、破坏性回滚与硬件操作。已有授权仍有效，新增越界范围另行确认。
